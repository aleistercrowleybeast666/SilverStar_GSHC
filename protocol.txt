二代飞控实验用极简协议
版本：exp-min-v1

设计目标：
1. 实验阶段优先保证简单、低开销、易实现。
2. 删除天地 AGP 中不必要的 SOF / VER / LEN / FLAGS / 应用层 CRC。
3. 天地无线包依赖 SX1281 LoRa PHY 的包长度与 PHY CRC。
4. 地面站与上位机串口仍保留最小帧头、长度和 CRC，因为 UART 是字节流，必须分帧。
5. 主遥测 5 Hz：一包回传加速度 raw、角速度 raw、四元数 q15、速度 float、位置 float。
6. 不实时回传磁场、气压、欧拉角。
7. 磁场、气压、高频原始 IMU、完整调试量写入飞控 TF 卡。

============================================================
1. 速率与可行性
============================================================

厂家参考距离 3 km 条件为：
- 空旷晴朗
- 两端 5 dBi 天线
- 天线高度约 2.5 m
- 空中速率约 1 kbps

现在目标：
- 1000 m 内稳定通信
- 一端 2 dBi，一端 5 dBi
- 推荐空中速率先测 3~4 kbps

链路余量粗估：
- 距离 3 km -> 1 km，链路预算增加约 9.5 dB
- 天线 5+5 dBi -> 2+5 dBi，损失约 3 dB
- 净余量约 6.5 dB

结论：
- 4 kbps 做 1000 m 通信是“有希望、值得测试”的档位，但不能不测试就保证。
- 如果 4 kbps 不稳，降到 2~3 kbps。
- 如果 4 kbps 很稳，可以继续保持 5 Hz 遥测。
- 若要 2 km，建议回到 1 kbps 级别，并降低遥测频率。

主遥测包 AIR_FLIGHT_STATE：
- 空中 payload = 50 byte
- 5 Hz 裸数据量 = 50 * 8 * 5 = 2000 bit/s

因此：
- 1 kbps：不可能 5 Hz
- 2 kbps：理论刚好，不建议
- 4 kbps：5 Hz 比较合理，但需实测
- 6 kbps：余量更好，但距离余量降低

============================================================
2. 通用约定
============================================================

字节序：
- Little Endian

数值格式：
- int16_t：有符号 16 位整数
- uint8_t / uint16_t / uint32_t：无符号整数
- float：IEEE754 float32

单位：
- accel_raw：IMU 加速度计原始计数 int16_t
- gyro_raw：IMU 陀螺仪原始计数 int16_t
- quat_q15：四元数 q15，int16_t，32767 对应 +1.0
- velocity：m/s，float32
- position：m，float32
- time_ms：飞控系统毫秒计时，uint32_t

换算：
accel_mps2 = accel_raw / 32768.0 * ACCEL_FULL_SCALE_G * 9.80665

gyro_radps = gyro_raw / 32768.0 * GYRO_FULL_SCALE_DPS * pi / 180.0

quat_float = quat_q15 / 32767.0
接收端恢复四元数后应重新归一化。

注意：
- IMU 量程必须在飞控、上位机、后处理中保持一致。
- 或者在日志说明中记录 ACCEL_FULL_SCALE_G 和 GYRO_FULL_SCALE_DPS。
- 若 quat_q15 四项全为 0，接收端必须标记 quat_valid=0 / invalid/raw=0。
  上位机可用单位四元数作为 3D fallback，但不能把它当作有效姿态。

============================================================
3. 天地无线协议 AIR
============================================================

无线包直接作为 SX1281 LoRa payload。
不再包含 SOF、版本、长度、FLAGS、应用层 CRC。

所有 AIR 包统一格式：

Byte 0      AIR_TYPE
Byte 1      SEQ
Byte 2..    BODY，由 AIR_TYPE 决定

说明：
- AIR_TYPE 用于区分遥测、状态、命令、应答。
- SEQ 为 0~255 循环序号。
- 无线包长度由 LoRa 接收函数给出。
- 错误包由 LoRa PHY CRC 过滤。
- 高频遥测不做 ACK。

------------------------------------------------------------
3.1 AIR_TYPE 定义
------------------------------------------------------------

0x10  AIR_FLIGHT_STATE     空端 -> 地面站，主遥测包
0x20  AIR_STATUS           空端 -> 地面站，状态事件
0x30  AIR_CMD              地面站 -> 空端，命令
0x40  AIR_ACK              空端 -> 地面站，命令应答

============================================================
4. AIR_FLIGHT_STATE：主遥测包
============================================================

方向：
空端 -> 地面站 -> 上位机

用途：
5 Hz 实时回传主要飞行状态。

格式：

Byte 0      AIR_TYPE = 0x10
Byte 1      SEQ

Byte 2~5    TIME_MS        uint32_t

Byte 6~7    ax_raw         int16_t
Byte 8~9    ay_raw         int16_t
Byte 10~11  az_raw         int16_t

Byte 12~13  gx_raw         int16_t
Byte 14~15  gy_raw         int16_t
Byte 16~17  gz_raw         int16_t

Byte 18~19  qw_q15         int16_t
Byte 20~21  qx_q15         int16_t
Byte 22~23  qy_q15         int16_t
Byte 24~25  qz_q15         int16_t

Byte 26~29  vx             float，m/s
Byte 30~33  vy             float，m/s
Byte 34~37  vz             float，m/s

Byte 38~41  x              float，m
Byte 42~45  y              float，m
Byte 46~49  z              float，m

总长度：
50 byte

说明：
- 加速度和角速度为 IMU raw，不是物理单位。
- 四元数为 q15 压缩值。
- 四元数 raw 位于 AIR frame byte18/20/22/24；经 GSP_AIR_RX 转发后对应 GSP payload byte21/23/25/27。
- 若 quat_q15 = 0,0,0,0，上位机显示 invalid/raw=0。这通常表示飞控 IMU 未收到或未开启 JY901B 0x59 Quaternion Pack，不表示 GSP_AIR_RX 偏移错误。
- 速度和位置仍用 float32。
- 位置推荐使用相对起飞点坐标。
- 若使用 NED，z 轴向下；若使用 ENU，z 轴向上。上位机与后处理必须统一。

推荐频率：
- 4 kbps：5 Hz
- 2~3 kbps：2~3 Hz
- 1 kbps：约 1 Hz

============================================================
5. AIR_STATUS：状态事件
============================================================

方向：
空端 -> 地面站 -> 上位机

格式：

Byte 0      AIR_TYPE = 0x20
Byte 1      SEQ
Byte 2      STATUS_ID
Byte 3~6    TIME_MS        uint32_t
Byte 7      ARG0
Byte 8      ARG1

总长度：
9 byte

STATUS_ID：
0x01  BOOT
0x02  SELFTEST_OK
0x03  MISSION_START
0x04  LAUNCH
0x05  PARACHUTE_DEPLOY
0x06  LANDING
0x07  LOCKED
0x08  UNLOCKED

建议：
- 关键状态重复发送 2~3 次。
- 重复发送时 STATUS_ID 和 TIME_MS 保持一致。
- 上位机根据 STATUS_ID + TIME_MS 去重。

============================================================
6. AIR_CMD：命令
============================================================

方向：
上位机 -> 地面站 -> 空端

格式：

Byte 0      AIR_TYPE = 0x30
Byte 1      SEQ
Byte 2      CMD_ID
Byte 3~6    TOKEN          uint32_t
Byte 7      PARAM0
Byte 8      PARAM1

总长度：
9 byte

CMD_ID：
0x01  START_MISSION
0x02  PING
0x03  LOCK
0x04  UNLOCK

START_MISSION：
- TOKEN = 0xA55A3CC3
- PARAM0 = 0：只开始任务
- PARAM0 = 1：开始任务，同时点火
- 仅 UNLOCKED 状态允许执行

PING：
- TOKEN 任意
-任务开始前有效
- 不改变状态

LOCK：
- TOKEN = 0xC33CA55A
- 任务开始前有效
- 已 LOCKED 时可返回 OK

UNLOCK：
- TOKEN = 0x55AA6996
- 任务开始前有效
- 任务开始后建议返回 BAD_STATE 或 REJECTED

============================================================
7. AIR_ACK：命令应答
============================================================

方向：
空端 -> 地面站 -> 上位机

格式：

Byte 0      AIR_TYPE = 0x40
Byte 1      SEQ
Byte 2      ACK_SEQ        被应答 AIR_CMD 的 SEQ
Byte 3      ACK_CMD_ID     被应答命令 CMD_ID
Byte 4      RESULT
Byte 5~8    TIME_MS        uint32_t

总长度：
9 byte

RESULT：
0x00  OK
0x01  BAD_LEN
0x02  BAD_CMD
0x03  BAD_TOKEN
0x04  BUSY
0x05  REJECTED
0x06  BAD_STATE
0x07  LOCKED_REQUIRED
0x08  ALREADY_LOCKED
0x09  ALREADY_UNLOCKED

建议：
- 所有 AIR_CMD 都等待 AIR_ACK。
- 超时可重发 2~3 次。
- AIR_FLIGHT_STATE 和 AIR_STATUS 不需要 ACK。
- AIR_ACK 是上位机命令按钮状态转换的依据，不只是日志记录。

上位机 ACK 后置按钮状态机：
- 初始 assumed LOCKED：LOCK disabled, UNLOCK enabled, START disabled。
- 发送任意 AIR_CMD 后，若已有 pending，拒绝发送新命令。
- LOCK 只有收到匹配 AIR_ACK 且 RESULT=OK 或 ALREADY_LOCKED 后，才切到 LOCK disabled, UNLOCK enabled, START disabled。
- UNLOCK 只有收到匹配 AIR_ACK 且 RESULT=OK 或 ALREADY_UNLOCKED 后，才切到 LOCK enabled, UNLOCK disabled, START enabled。
- START_MISSION 只有收到匹配 AIR_ACK 且 RESULT=OK 后，才切到 PING/LOCK/UNLOCK/START 全 disabled，数据处理工具 disabled。
- ACK 未匹配本机 pending，不改变按钮状态。
- BAD_TOKEN / BAD_STATE / LOCKED_REQUIRED / BUSY / REJECTED / TIMEOUT 不改变按钮状态，只更新提示；超时清除 pending 后允许用户重发。
- STATUS LOCKED/UNLOCKED 只在没有 LOCK/UNLOCK pending 时同步按钮，避免状态事件早于 ACK 导致 UI 提前切换。
- STATUS MISSION_START/LAUNCH/PARACHUTE_DEPLOY/LANDING 可切 mission 状态；若 START pending 尚未 ACK，MISSION_START 等任务状态可视为任务已开始并清除 START pending。

============================================================
8. 地面站-上位机串口协议 GSP-MIN
============================================================

UART 是字节流，因此必须保留最小帧头、长度和 CRC。
但删除原 GSP 中的版本和序号。

------------------------------------------------------------
8.1 GSP-MIN 总体帧格式
------------------------------------------------------------

Byte 0      SOF1 = 0xA5
Byte 1      SOF2 = 0x5A
Byte 2      GSP_TYPE
Byte 3      LEN           payload 长度，0~255
Byte 4..    PAYLOAD
最后2字节   CRC16         对 GSP_TYPE、LEN、PAYLOAD 做 CRC16

总长度：
6 + LEN byte

说明：
- CRC16 使用 CCITT-FALSE，低字节在前。
- UART 层必须保留 SOF/LEN/CRC，否则很难从串口错位中恢复。
- GSP-MIN 不理解 AIR 业务，只做转发和地面站状态。

------------------------------------------------------------
8.2 GSP_TYPE 定义
------------------------------------------------------------

0x01  GSP_GS_STATUS       地面站状态
0x02  GSP_AIR_RX          地面站转发收到的 AIR 包给上位机
0x03  GSP_AIR_TX          上位机要求地面站发送 AIR 包
0x04  GSP_ACK             GSP 层应答

============================================================
9. GSP_GS_STATUS
============================================================

方向：
地面站 -> 上位机

PAYLOAD：

Byte 0      GS_STATE
Byte 1      RADIO_STATE
Byte 2~5    TX_CNT          uint32_t
Byte 6~9    RX_CNT          uint32_t
Byte 10~11  CRC_ERR_CNT     uint16_t

PAYLOAD 长度：
12 byte

GS_STATE：
0x00 IDLE
0x01 INIT_OK
0x02 RX_MODE
0x03 TX_MODE
0x04 ERROR

RADIO_STATE：
0x00 NOT_INIT
0x01 READY
0x02 RX
0x03 TX
0x04 BUSY

推荐频率：
- 1 Hz

============================================================
10. GSP_AIR_RX
============================================================

方向：
地面站 -> 上位机

用途：
地面站收到 AIR 包后，加上链路质量信息，转发给上位机。

PAYLOAD：

Byte 0      RSSI_DBM       int8_t，单位 dBm
Byte 1      SNR_Q4         int8_t，单位 0.25 dB
Byte 2      AIR_LEN        uint8_t
Byte 3..    AIR_FRAME      原始 AIR 包

PAYLOAD 长度：
3 + AIR_LEN

说明：
- 实际 SNR = SNR_Q4 / 4.0
- AIR_FRAME 起始偏移固定为 payload[3]，就是第 3~7 节定义的 AIR 包。
- 上位机根据 AIR_TYPE 解析 AIR_FRAME。
- 对 AIR_FLIGHT_STATE，qw/qx/qy/qz 位于 AIR frame byte18/20/22/24，因此经 GSP_AIR_RX 后位于 GSP payload byte21/23/25/27。

============================================================
11. GSP_AIR_TX
============================================================

方向：
上位机 -> 地面站

用途：
上位机要求地面站发送一帧 AIR 包。

PAYLOAD：

Byte 0      AIR_LEN
Byte 1..    AIR_FRAME

PAYLOAD 长度：
1 + AIR_LEN

说明：
- 主要用于发送 AIR_CMD。
- 地面站不解释 AIR_CMD，只负责无线发送。
- 地面站可检查 AIR_LEN 是否超过最大无线 payload。

============================================================
12. GSP_ACK
============================================================

方向：
地面站 -> 上位机，或上位机 -> 地面站

用途：
确认 GSP-MIN 帧是否正确接收。
不替代 AIR_ACK。

PAYLOAD：

Byte 0      ACK_GSP_TYPE
Byte 1      RESULT
Byte 2      DETAIL

PAYLOAD 长度：
3 byte

RESULT：
0x00 OK
0x01 BAD_CRC
0x02 BAD_LEN
0x03 BAD_TYPE
0x04 BAD_PARAM
0x05 BUSY

============================================================
13. 推荐运行策略
============================================================

1000 m / 4 kbps 推荐：
- AIR_FLIGHT_STATE：5 Hz
- AIR_STATUS：事件触发，关键事件重复 2~3 次
- AIR_CMD：只在上位机操作时发送
- AIR_ACK：命令应答
- GSP_GS_STATUS：1 Hz

1000 m / 2~3 kbps 保守：
- AIR_FLIGHT_STATE：2~3 Hz
- AIR_STATUS：事件触发
- AIR_CMD/AIR_ACK：命令时发送
- GSP_GS_STATUS：1 Hz

1 kbps 极限距离：
- AIR_FLIGHT_STATE：1 Hz 或更低
- AIR_STATUS：事件触发
- 不建议 5 Hz
